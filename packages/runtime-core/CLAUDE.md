# @spectrum/runtime-core

**Responsibility:** the shared composition root for both `apps/cli` and `apps/desktop`. Owns the base `AppContext` type, `createAppContext(deps)` (flat, logic-free wiring of real `@spectrum/*` adapters), and `CreateAppContextDeps`/`realDeps`.

**Public surface:** `src/index.ts` re-exports `AppContext`, `CreateAppContextDeps`, `createAppContext`, `realDeps`, `ProviderTestResult`, and runner-extension-point types from `src/app-context.ts` / `src/create-app-context.ts` / `src/deps.ts`.

**Depends on:** every `@spectrum/*` leaf the factory wires (agent-driver, agent-events, config, data-admin, db, driver-*, extensions, harnesses, logger, platform, proc, projects, provider-host, providers, proxy, run-store, secrets, sessions, types, utils). NOT `ipc`/`ui`/`brand`/`cli` (GUI- or CLI-app concerns).

**Effects owned:** ALL real adapter construction (fs/keychain/sqlite/process/server) — but only inside `createAppContext`, behind the `CreateAppContextDeps` seam. `realDeps` is the production wiring.

**Local rules:** NEVER import `electrobun` — enforced by `src/boundary.test.ts`. GUI-only seams (`createRunManager`, `startRunnerSocket`, `createRendererWatchdog`, `removeDir`, `relaunch`) and the `RunManager` itself live in `apps/desktop`'s `createGuiContext`, not here. Runner-extension-point fields on `AppContext` (`sessionSink`, `runStore`, `routingDriver`, `resolveResumeInput`, `resolveModelEnv`, `flowRunner`, `closeDb`, `clock`) are typed + documented "GUI runner extension points"; the CLI never reads them. `createAppContext` is flat and logic-free; every decision lives in the injected adapters.

Provider-plugin state is the one exception to "flat": `createAppContext` is SYNCHRONOUS but reading extensions from disk is not, so the plugin-derived values (`providerRegistry`, the extension registry, the supervised-contribution set) live in mutable cells that `refreshExtensions()` swaps. Consumers — including `AppContext.providerRegistry` and `AppContext.extensionRegistry` — are handed a STABLE delegating façade, never the cell's current value, which would go stale on the first swap. Refreshes are SERIALIZED and their FIVE cells (`extensionRegistryCell`, `enabledExtensionIds`, `supervisedIds`, `supervisedOwners`, `providerRegistryCell`) swap in ONE synchronous block: a torn view (a new supervised set against the previous provider registry) would make a supervised contribution look unsupervised, and an unsupervised plugin resolves to no base url at all. `resolveBaseUrl` awaits the refresh IN FLIGHT, not merely the first one. A failed load is logged (`{ kind }`) and swallowed; at startup that means builtins only, but a LATER failure keeps the last known-good view rather than demoting live plugins.

SECURITY: `enabled` is applied on EVERY plugin-derived path, not just `providerDescriptors` — the supervised set and the `isEnabled` gate the provider host consults are both built from `cfg.providerPlugins`. A disabled extension that reached either would have its `launch.command` spawned with the resolved secrets of whichever provider record named its contribution id. Model discovery goes through the same `resolveBaseUrl` seam as the factory, so a supervised plugin's models resolve against its live loopback port and a plugin-keyed descriptor can never send its `Authorization` header to a manifest-supplied host. Supervised children are swept with `providerHost.retainOnly` on every config save and every refresh — the instance key derives from the provider's config and secret refs, so an unswept edit leaves the previous child running with the superseded secrets. The sweep re-evaluates `enabled` against the config it is HANDED (via `supervisedOwners`, which maps every installed supervised contribution to its owning manifest) rather than reading `supervisedIds`: disabling a plugin is a save, not a refresh, so the stale set would retain the key and leave the disabled extension's child alive.

SECURITY: a live SETUP FLOW runs on its own supervised child keyed `flow:<contribution id>:<nonce>` — a key that belongs to no provider record, so the configured-provider retain-set alone would stop it mid-flight, including on the very `config.save` that persists the flow's own output. The sweep unions in `flowRunner.activeInstanceKeys()`, read AT SWEEP TIME (a flow that ended between two sweeps must not be retained) and filtered by the SAME `enabled` set and `supervisedOwners` translation the provider branch uses — a flow key's middle segment is a CONTRIBUTION id, not the MANIFEST id `enabled` is keyed by. Flows of a disabled extension are deliberately NOT retained: disabling mid-flow withdraws consent from a process that may be holding a half-finished credential exchange. `flowRunner.abandon(dropped, "extension-disabled")` runs immediately BEFORE `providerHost.retainOnly` on every sweeping path — `retainOnly` stops and forgets with no callback and no reason code and `host.status` cannot tell a swept child from a crashed one, so an `abandon` without a following `retainOnly` leaks the child and a `retainOnly` without a preceding `abandon` gives the user a raw transport error instead of a named "no longer enabled" step. `AppContext.flowRunner.takeCompletion` returns PLAINTEXT secrets: GUI flow handler only.

KNOWN GAP (deliberate): `ExtensionAdmin.remove` stops a contribution's children with `providerHost.stopAllFor`, which is NOT a sweep and does not `abandon` first, so a flow live across an uninstall sees the raw transport failure until the `config.save` at the end of `remove` sweeps (and abandons) it. `shutdown`'s `providerHost.stopAll()` likewise does not abandon — the process is exiting and there is no UI left to notify.

KNOWN GAP (deliberate): model discovery requires a loopback base url for EVERY plugin-keyed descriptor, supervised or user-run, and never accepts a manifest-supplied `defaultBaseUrl`. The factory path enforces only "must resolve to some url". So a user-run plugin server on a LAN host can serve chat but cannot list models. Neither path draws a supervised/user-run line — discovery is strict everywhere, the factory is weak everywhere.

SECURITY: a `plugin:`-keyed descriptor that resolves to no base url is REFUSED (`bad-request`), never left to the SDK's own default — plugin descriptors carry no `defaultBaseUrl`, so falling through would aim the request, and the plugin's secrets, at the AI SDK's cloud endpoint.
