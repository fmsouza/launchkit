# apps/desktop (spectrum binary)

**Responsibility:** the dual-mode entry (`detectMode` -> CLI vs GUI) + the GUI shell (window, tray, IPC handlers) + React pages; the ONE place real effects are constructed and injected into the packages.

**Public surface (not a library -- the user-facing `spectrum` binary):** `src/main.ts` (entry: `runApp(detectMode(argv), argv, realDeps)`); `src/app.ts` (`runApp` mode router); `src/composition.ts` (`AppContext` + `createAppContext` real-adapter wiring); `src/gui/window.ts` (`openWindow` Electrobun seam); `src/gui/ipc/handlers.ts` (`createIpcHandlers` binding the ipc contract to subsystems). Owned by OTHER plans: `src/gui/tray.ts` (tray-and-polish), `views/**` (gui-pages), `src/detect-mode.ts` (phase0).

**Depends on:** every `@spectrum/*` package (`cli`, `proxy`, `harnesses`, `config`, `sessions`, `secrets`, `ipc`, `ui`, `types`, `utils`).

**Effects owned:** ALL of them -- but only via constructing the real adapters in `composition.ts` and injecting them. `createAppContext` is flat and logic-free; every decision lives in `runApp` / `createIpcHandlers` (separately unit-tested with fakes). Electrobun (window + message bus) lives behind thin injected seams in `gui/window.ts` so the logic is testable without a running window.

**Local rules:** this is the only place real fs/keychain/sqlite/process/server adapters are built. SECURITY: a `Provider` is ALWAYS projected to a `ProviderView` before crossing IPC (no secret value or `ref` to the webview); `setProviderSecret` is the only inbound secret path and writes straight to the keychain, persisting only the returned `SecretRef`; the proxy is started bound to loopback (`config.settings.proxyHost` = `127.0.0.1`) with a per-run key. Confirm Electrobun's `BrowserWindow`/IPC API against current docs and adapt only the `gui/window.ts` seam if it diverges.
- **Provider setup flows** (`startProviderFlow`/`advanceProviderFlow`/`cancelProviderFlow` in `gui/ipc/handlers.ts`) are the security boundary for extension-driven setup: `done.secrets` NEVER crosses IPC. The handler drains `flowRunner.takeCompletion` main-side, validates the record the way `addProvider` does, writes each secret VALUE through `SecretStore.set`, saves the provider (config file gets refs only), and returns a `done` step REBUILT from its message alone. An extension-supplied url reaches the OS opener only through `ctx.openExternalGuarded` (`createGuardedOpenExternal`, built in `composition.ts`); the raw `openExternalUrl` stays for Spectrum's own `file://` urls, which the guard refuses. `flowOrigins` (per handler set) is what a completed flow is persisted AGAINST — never a renderer-supplied provider key. A `PluginError` becomes user-facing copy via `gui/ipc/flow-errors.ts`, which deliberately drops the extension's own `detail` — and, for `not-found`, its `id` too: that id is a contribution id when a flow fails to START and the Spectrum-side session handle when a STEP fails, so the copy is chosen by the `FlowCallKind` the call site passes rather than by interpolating an id whose meaning changes underneath it. `invalid-manifest` splits on CAUSE the same way: a contribution that offers a setup flow but declares no `launch` block is matched by `NO_LAUNCH_BLOCK_DETAIL` (imported from `@spectrum/provider-host`, never hand-copied) and told exactly that, while a step this Spectrum cannot parse keeps the "needs a newer Spectrum" copy — the same kind, two causes, and only one of them is fixed by upgrading.
- The cross-platform keychain backend is selected by `createPlatformKeychainBackend({ platform })` (macOS Keychain / Linux Secret Service / Windows DPAPI-file); `createAppContext` stays flat — the OS branch lives in the selector.
- The system tray (`src/gui/tray.ts`) is built from the PURE `buildTrayMenu` descriptor (`src/gui/tray-menu.ts`); the native Electrobun Tray lives only behind the `MountTrayDeps.createTray` seam, and a Launch click reuses the same `ctx.runner.launch` (native-run) path as the IPC `launchHarness` handler — the manager owns session creation, so the tray no longer calls `ctx.sessions.create` itself. Every launchable harness is native; a harness with no registered driver is skipped. (The headless `ctx.launch` + inherit-stdio spawner is now CLI-only.)
- The GUI login-shell PATH probe (`enrichGuiPathAsync`) runs ASYNC and memoized off the Worker's startup hot path (never `Bun.spawnSync` at startup); harness launch awaits `ctx.ensureGuiPathResolved()` before resolving a command. Synchronous subprocess spawn on the packaged-GUI startup path causes a nondeterministic `EXC_BREAKPOINT`/`brk 1` Worker crash (regression guard in `main.test.ts`).
- The window opens only AFTER `startProxy().ready` settles (config load → proxy start), bounded by `StartupWait.capMs` (`main.ts`). Opening the webview mid-startup-burst lets Electrobun's native threads drive bun:ffi JSCallback traffic (navigation events, `views://` mime lookups — non-threadsafe, sync-return) into the busy Worker VM and corrupts JSC — the post-update `EXC_BREAKPOINT`/PAC-IB startup crash, fifth incident of the packaged-GUI startup-window class after #94/#98/#99/#100 (regression tests: `main.test.ts` "main startup sequencing"). Never add work between window open and renderer connect; put startup work before `openWindow()` (gated) or defer it behind on-demand awaits like the PATH probe.
